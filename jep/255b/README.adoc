== Abstract

How a cluster of controllers built on JEP-250 to JEP-257 is installed, scaled, upgraded, rolled back, migrated to, backed up and restored, and what it costs. This is guidance for operators and for whoever maintains the Helm chart, not a standard: the behaviour it relies on is specified in the other JEPs. It may become documentation in the chart's repository instead of a JEP.

== Specification

=== What a controller needs

* *The stores:* the database's JDBC URL and credentials (`+CLUSTER_POSTGRES_URL+`, `+CLUSTER_POSTGRES_USER+`, `+CLUSTER_POSTGRES_PASSWORD+`) and the blob store's (Azure: `+CLUSTER_AZURE_BLOB_CONNECTION_STRING+`, `+CLUSTER_AZURE_BLOB_CONTAINER+`; S3: `+CLUSTER_S3_BUCKET+`, `+CLUSTER_S3_PREFIX+`, `+CLUSTER_S3_REGION+`, `+CLUSTER_S3_ENDPOINT+`, `+CLUSTER_S3_PATH_STYLE+`, with credentials from the AWS default chain). Access to these is what makes a controller part of the cluster (JEP-255a).
* *The cluster's key material:* `+secret.key+`, `+secrets/+` and the instance identity, generated once for the cluster and given to every controller. The chart's `+make-seed-secret.sh+` creates it as a Kubernetes Secret, and the entrypoint copies it into an empty home. A controller started without it refuses to start (JEP-255a).
* *An identity:* a name unique among the live controllers (`+JENKINS_CLUSTER_NAME+`, by default the host name, such as the pod name) and an internal URL the other controllers can reach it at (`+JENKINS_CLUSTER_INTERNAL_URL+`).
* *Settings the chart makes:* Stapler's bound-object id prefix set to the controller's name (`+org.kohsuke.stapler.bind.BoundObjectTable.idPrefix+`), and every form sign-in issuing a remember-me cookie (`+TokenBasedRememberMeServices2.alwaysRemember+`), both for JEP-254. A configured root URL (forwarding does not pass the `+Host+` header on).
* *An artifact manager* (JEP-202) keeping artifacts and stashes in shared storage. Every cluster needs one (JEP-252).
* *A compatible version:* the same image, or an adjacent version during a rolling upgrade.

=== The Helm chart

`+charts/jenkins-cluster+`:

* a StatefulSet of N controllers with `+emptyDir+` homes, and a Service without stickiness
* the seeded key Secret
* JCasC, with an option for in-chart Postgres and Azurite (the Azure Storage emulator) for development; managed services in production
* a Kubernetes cloud, and the artifact manager (azure-artifact-manager, `+artifactManager.*+`) in the blob container. Its storage credential is created at startup if absent, not declared in JCasC: JCasC replaces the system credentials it declares, and every controller that starts applies it, through the shared store
* JCasC that keeps nodes it does not declare (configuration-as-code's `+keepUndeclaredNodes+`), so that one controller applying the YAML does not delete the cluster's other nodes
* probes: readiness reflects whether the controller is ready (JEP-255a). The startup probe SHOULD allow at least the boot wait (10 minutes by default), or the kubelet restarts a controller that is waiting for its stores
* for managed services: the store settings from an existing Secret (`+store.existingSecret+`), TLS options for the JDBC URL (`+postgres.urlParameters+`, for example `+sslmode=verify-full+`), the connection pool's size (`+store.poolSize+`) and the session-lock switch (`+store.sessionLocks+`)

=== StatefulSet or Deployment

Either works: nothing depends on a controller keeping its name. Membership, leases and adoption go by origin, a new one per start (JEP-255a), and the internal URL can be a pod IP (`+http://$(POD_IP):8080/+`). The acceptance tests exercise only the chart's StatefulSet. It uses one for:

* stable, readable names (`+cnj-0+`, `+cnj-1+`) in the cluster view and logs, and per-pod DNS through a headless Service
* one-at-a-time rolling updates, which keep the number of controllers adopting builds predictable
* pod management `+Parallel+`, so a scale-up or a restart of all pods does not wait for each pod in turn

=== No persistent volumes for controllers

`+JENKINS_HOME+` is a cache: everything that must survive is in the stores, and an empty home is rebuilt from them at start. So the chart uses `+emptyDir+`, which survives a container restart (a safe restart, or a crash) but not a rescheduled pod. Persistent volumes would make failover worse: a volume that can be attached to one node at a time keeps a replacement pod waiting while it detaches from a dead node (minutes, typically), and binds pods to the volume's zone.

What a fresh home costs is the start. Measured on a laptop (Docker, 8 CPUs), with every plugin in the image:

[cols="3,2"]
|===
| Case | Time

| Fresh controller, 2,000 jobs and 2,000 builds in the stores: API served after the container started | 12.8–20.4 s (median 16.4 s, three runs): 2.6–4.9 s container and JVM, 7–11 s Jenkins initialisation
| Its first full page of 2,000 jobs | 5–19 s more, then 0.6 s warm
| The same, with one plugin installed at runtime and loaded live | 12.9 s
| Three controllers on 200,000 build records, started together | 18 s
| A job page with 20,000 builds, on each of three controllers | 0.6–0.8 s cold, 0.02–0.03 s warm
| Deleting a job with 20,000 builds | 1 s
| Two controllers, 2,000 jobs: the second lists the jobs after the first starts creating them | 10 s
| Restart of a controller with its home | 14 s
| 50 running Pipelines adopted after their controller is lost | within 24 s
|===

A fresh controller now fetches runtime-installed plugins before it loads anything and restarts once (JEP-256), which adds a JVM start that has not been measured. To start faster, put plugins in the image rather than installing them at runtime, and size `+emptyDir+` (or `+medium: Memory+`) for the builds people look at.

=== Rolling upgrades

`+helm upgrade+` to a new image replaces controllers one at a time. Running Pipelines are adopted by the controllers still up, and mixed versions coexist within one protocol number (JEP-255a).

*Mixed versions: limitation.* Compatibility during a roll is guaranteed for the store protocol and the schema, not for the shape of serialised objects. If a new version of core or of a plugin adds a field, and a controller still running the old version saves the same object, the old controller writes it without the field, and the new controller reloads it with the field reset (JEP-250 reloads with `+updateByXml+` semantics). A `+readResolve+` that renames elements has the same effect in both directions, and each side's save then looks like a change to the other's, so a save may be refused and reloaded. The same applies to a plugin roll (JEP-256). Configuration SHOULD NOT be changed while a roll is in progress. JCasC is applied by each controller as it starts, so the new version's fields can be lost again by an old controller that saves afterwards.

=== Rolling back

* *Before Contract* of the new version's migrations (JEP-255a), deploying the previous image (a rolling upgrade in the other direction) restores the previous version; the schema is a superset of both.
* *After Contract*, the protocol it needed is the cluster's floor, and an image with an older protocol refuses to start. The way back is to restore the database and blob store from a backup taken before the upgrade, into a new namespace, and start the previous image on it. Builds that ran after the backup are lost.
* *Plugins:* a plugin downgrade is refused (JEP-256). Going back to an older plugin set means an image with the older set and a store restored to before the change.
* Contract runs shortly after a roll finishes, so the window for rolling back by image is short (see Open questions).

=== Importing a file-based home

A file-based home is imported by starting one controller on it with `+importHome=true+`. Configuration, users, credentials, nodes, builds, logs and fingerprints are uploaded, keys already present are kept, and a report is written. Importing again imports nothing.

=== Backup and restore

* `+scripts/backup.sh+` does a `+pg_dump+` and then copies the blob store; `+scripts/restore.sh+` restores into a new namespace. The backup is consistent when no controller is running (scale the StatefulSet to 0 first). Taken while controllers run, it can restore records of builds deleted or republished during the copy with their files missing or newer. For an online backup, use point-in-time recovery.
* After a restore, builds that were running at backup time are adopted from their save points, or closed as aborted (JEP-252).
* *Point-in-time recovery.* Postgres is restored with its own tools (a base backup plus archived WAL, or a managed service's restore to a time) into a new database, and fresh controllers are started on it. The blob store must be restorable to the same point too; Azure Blob Storage's versioning and point-in-time restore do this. The cluster deletes blobs with their records (there is no deferred deletion), so without blob versioning a restore to an earlier time finds the records of builds deleted since, with their files gone.

=== Downgrading Jenkins

A controller on a version without these JEPs cannot use the cluster's stores. An item's `+config.xml+` taken from a cluster carries `+<itemUuid>+`, which an older version reports as unknown data until the item is saved again (JEP-250). Downgrading a cluster is done by restoring a backup, as above.

== Motivation

Single-controller Jenkins has no equivalent for joining, upgrading, rolling back or restoring a cluster. The standards (JEP-250 to JEP-257) say what the software does; an operator needs to know what to set up and what to expect.

== Reasoning

* *A chart, not instructions.* The settings a controller needs (stores, seed, identity, Stapler and session properties, artifact manager, probes) are easy to get partly wrong; the chart sets them together.
* *Ephemeral homes* follow from the stores holding everything that must survive, and give the fastest failover.
* *Informational:* nothing here constrains an implementation that the other JEPs do not already constrain.

== Backwards Compatibility

Not applicable: the chart and scripts are new.

* *Known limitations:*
** Point-in-time recovery needs blob versioning, which the Azure Storage emulator lacks; it is exercised for Postgres only.
** A fresh controller's first full page of 2,000 jobs takes 5–19 s (0.6 s warm). It can be made faster (bulk reads or lazy loading are candidates); not profiled yet.

== Security

* The store and blob credentials come from Secrets, and connections SHOULD use TLS (`+postgres.urlParameters+`, the blob connection string).
* The controllers' internal URLs must stay inside the cluster network. The chart's example internal URL is plain HTTP; traffic between controllers carries users' credentials (JEP-254) and SHOULD use TLS (a service mesh, or an HTTPS internal URL).
* The trust model is in JEP-250 and JEP-255a: whoever can write to the stores controls every controller.

== Infrastructure Requirements

* a PostgreSQL database (a managed service, or in-chart for development) and a blob store (Azure Blob Storage or S3) per cluster, plus an artifact manager in shared storage
* repositories to host the plugins (`+cluster+`, `+cluster-postgresql+`, `+cluster-azure-blob+`, `+cluster-s3+`) and a place for the chart (jenkinsci/helm-charts, or next to the plugins); not decided
* Docker in the plugins' CI (Testcontainers)
* a Kubernetes cluster (kind) to run the acceptance scripts, and a decision on who runs them after acceptance and where they live (for example ATH, or a repository of their own)

== Open questions

* Should Contract of a migration be started by an operator, or wait for a grace period after a roll, so that rolling back by image stays possible for a time?
* Should this be documentation in the chart's repository rather than a JEP?
